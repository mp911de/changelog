= Changelog Reference Documentation
:toc: left
:toclevels: 2

You do not need to read this document to use the tool.
It explains why a change appears (or is missing) in the generated release notes and how commit messages and configuration affect the changelog.

== Writing good commit messages

A changelog is only as good as the commit history it is generated from.
Two short articles cover the conventions assumed throughout this document:
https://cbea.ms/git-commit/[How to Write a Git Commit Message] and
https://tbaggery.com/2008/04/19/a-note-about-git-commit-messages.html[A Note About Git Commit Messages].

In summary:

* Separate the subject from the body with a blank line.
* Keep the subject short and write it in the imperative mood, for example `Skip type inspection for transient properties`.
* Do not end the subject with a period.
* Use the body to explain what changed and why, not how.
* Wrap the body at a readable width.

=== Ticket References are Breadcrumbs

A ticket reference connects a commit to the issue or pull request that motivated it.
Years after a change is merged, that link is often the only path back to the discussion, the reproduction, and the decision behind the code.
Recording it costs one line and pays off whenever someone has to understand why the code looks the way it does.

`changelog` reads these references to build release notes, so the discipline that helps future maintainers also produces accurate notes with no extra effort.

== Referencing tickets

Associate a commit with one or more https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue[GitHub issues or pull requests]; `changelog` discovers the references and picks the best match for changelog inclusion and contributor crediting.
A reference may be written in any of these forms:

[cols="1,2",options="header"]
|===
| Form | Example

| Plain reference
| `#1234` or `gh-1234`

| Cross-repository reference
| `spring-projects/spring-data-commons#1234`

| Issue or pull request URL
| `https://github.com/spring-projects/spring-data-commons/issues/1234`
|===

A `gh-1234` reference is normalized to `#1234`.
A cross-repository reference is resolved against the repository it names rather than the repository being released (see <<cross-repository-references>>).

The sections below start from the simplest reference and add context; every example is a real commit message.

=== A plain reference

The simplest reference is the ticket number on its own line.

[source]
----
Use `ConcurrentLruCache` in `PersistentPropertyPathFactory`.

#3493
----

The referenced ticket becomes a changelog entry.
A plain reference is the baseline, not an error or a fallback.

=== Closing a ticket

A closing keyword states that the commit resolves the ticket.
The recognized keywords are `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, and `resolved`.

[source]
----
Consider only instance `with` methods for property access.

Closes #3472
----

A closed ticket becomes a changelog entry, the same as a plain reference.
The difference shows once a message carries several references: a closing reference wins the entry selection (see <<combining-references>>).

=== Crediting a pull request

When a change is contributed through a pull request and then polished, forward-ported, or back-ported by a maintainer, record the originating pull request with an `Original pull request:` trailer.

[source]
----
Skip type inspection for transient properties.

Closes #3485
Original pull request: #3486
----

`Closes #3485` supplies the changelog entry; `Original pull request: #3486` credits the pull request author in the Contributors section (see <<crediting-contributors>>).
The credit is independent of the entry, so the maintainer who applied the commit does not displace the original contributor.

=== Pointing to related context

A `See` reference points to a related issue or pull request, frequently in another repository, that provides context for the change.

[source]
----
Remove deprecated methods.

See #2996
Closes #2995
----

Here `Closes #2995` supplies the entry and `See #2996` records the related ticket.
A `See` reference is most useful alongside a closing reference, and it accepts the cross-repository and URL forms:

[source]
----
Make reference to XML namespace optional.

Closes #2662
See https://github.com/spring-projects/spring-data-relational/issues/1290
Original pull request #2664
----

=== Recording related tickets

A `Related ticket:` (or `Related tickets:`) trailer records supporting tickets that the change touches without resolving.

[source]
----
Stop supporting params not annotated with `@ProjectedPayload`.

Closes #3301
Original pull request: #3453
Related ticket: #3298
----

Related tickets are context only: they become no changelog entry and credit no contributor.
Here `#3301` supplies the entry, `#3453` credits the contributor, and `#3298` is recorded without affecting the notes.

[[combining-references]]
=== Combining references

A commit message may carry references of several kinds; the kind decides what each contributes to the notes.
When more than one reference could supply the changelog entry, the strongest kind present wins, in this order:

. A closing reference (`Closes #1234`).
. A `See` reference (`See #1234`).
. An original pull request reference (`Original pull request: #1234`).
. A plain reference (`#1234`).

Alongside a closing or `See` reference, original pull request references are credit-only: the closing or `See` reference supplies the entry, and each original pull request reference still credits its author.
Roles are assigned before GitHub lookup; when the selected reference turns out missing, excluded, or private, an original pull request reference does not fall back into the entry role.

All references of the winning kind become entries; weaker kinds in the same message do not, and related references never do.
The precedence governs only the entry.
Contributor credit is independent: an `Original pull request:` reference always credits its author, even when a closing reference supplies the entry.

NOTE: Without a closing or `See` reference in the message, an `Original pull request:` reference supplies the changelog entry itself, so a pull request without recorded issue context still appears in the notes.

Across a run, a pull request recorded as the original pull request of another entry is not repeated as its own changelog entry.
For example, these two commits in one range:

[source]
----
Skip type inspection for transient properties.

Closes #3485
Original pull request: #3486
----

[source]
----
Polish transient property handling.

#3486
----

`#3485` supplies the changelog entry and `#3486` credits its author.
The plain `#3486` reference in the second commit is suppressed: the pull request is already credited alongside `#3485` and does not become a second entry.

Suppression is keyed on the ticket identity, not on commit order or the commit: every other entry reference to the same pull request in the run is omitted, while other references from the same commit still contribute entries.
It applies once the original pull request reference is followed, even when GitHub cannot resolve it; a reference held back by follow-reference policy creates no suppression.
Suppressed references are removed before section placement, so they do not appear under `--all` or in any configured section.

== How Changes become changelog entries

Each selected reference is resolved against GitHub to obtain the issue or pull request title, labels, and URL.
The resolved change is then placed into a section.

=== Sections and Labels

Sections are matched by label, in configuration order:

. *Exclusion.* If any label matches a configured excluded label, the change is omitted from the notes entirely.
. *First matching section.* The change is placed in the first configured section whose labels match one of the change's labels.
. *Unclassified.* If no section matches, the change is omitted by default, or collected under an `Other Changes` section when `--all` is given.

Because the first matching section wins, section order is significant.
Entries appear in the order their commits occur in the range.

Label matching is case-insensitive and anchored on word boundaries: a configured token matches a whole-word label, including the common `Category: Value` convention, but not a substring.

[cols="1,1,2",options="header"]
|===
| Configured token | Matches | Does not match

| `bug`
| `bug`, `Bug`, `Type: Bug`
| `debugging`, `non-bug`
|===

A reference whose ticket cannot be found (deleted, private, or a wrong number) produces no entry.

[[crediting-contributors]]
== Crediting Contributors

Changelog Tool appends a Contributors section that thanks the authors of contributed pull requests.
An author is credited through either path:

* A changelog entry that GitHub reports as a pull request credits its author.
* An `Original pull request:` reference credits its author, even if GitHub reports the ticket as an issue.
The commit message is the source of truth.

Authors listed in the `team` configuration are never credited. By default, the team contains the authenticated user.
Each contributor is listed once, sorted alphabetically ignoring case, with the login spelling GitHub returns.

== Selecting the commit range

Changelog Tool scans the non-merge commits in a range.
The range can be resolved from a single input (a version, a tag, or a maintenance branch) or given explicitly.
In both forms the lower bound is excluded and the upper bound is included.

[[releasing-a-version]]
=== Releasing a version

Given a single version, `changelog` resolves the commit range from the repository's tags and branches:

[source,shell]
----
changelog 4.0.4
----

Supported forms: SemVer (`4.0.0`), shortened forms (`4`, `4.0`), a `v` prefix (`v4.0.0`), Spring-style GA qualifiers (`4.0.0.RELEASE`, `4.0.0.Final`), service releases (`4.0.0.SR1`), and pre-releases (`4.0.0-M1`, `4.0.0-RC1`, `4.0.0.SNAPSHOT`).
A tag name releases the version its name spells, and a maintenance-branch name releases the branch's line (see <<maintenance-branch>>).

In the diagrams below, `<--` marks a resolved bound and `Range` is the result; <<resolution-rules>> states the underlying rules.

==== Patch

Before `4.0.4` is tagged, the upper bound is the tip of the `4.0.x` branch:

[source]
----
Generation: 4.0

 Branch:   4.0.x    <--  HEAD should be shipped 🚤 as 4.0.4
  Tags:    4.0.0
           4.0.1
           4.0.2
           4.0.3    <-- Previous version 🔀

 Range:    4.0.3..4.0.x
----

After `4.0.4` is tagged, the tag is the upper bound and the same notes are reproduced:

[source]
----
Generation: 4.0

 Branch:   4.0.x    <-- HEAD points to 4.0.5  💫
  Tags:    4.0.0
           4.0.1
           4.0.2
           4.0.3    <-- Previous version      🔀
           4.0.4    <-- Changelog upper bound 📦

 Range:    4.0.3..4.0.4
----

==== Minor

`4.1.0` opens the 4.1 line.
The lower bound is the previous minor's opener and the upper bound is `HEAD`:

[source]
----
Generation: 4.1

 Branch:   main     <-- HEAD opens 4.1   📦
           4.0.x
  Tags:    4.0.0    <-- Previous version 🔀
           4.0.1

 Range:    4.0.0..HEAD
----

==== Major

`4.0.0` opens the 4.0 line, before any `4.0.x` branch exists.
The lower bound is the opener of the previous major's most recent line (`3.5.0`, not its latest patch `3.5.1`):

[source]
----
Generation: 4.0

 Branch:   main     <-- HEAD opens 4.0   📦
           3.5.x
  Tags:    3.5.0    <-- Previous version 🔀
           3.5.1

 Range:    3.5.0..HEAD
----

[[maintenance-branch]]
==== Maintenance Branch

A maintenance-branch name (`4.0.x`) releases what accumulated on the line since its latest release: the lower bound is the line's latest release tag, the upper bound the branch tip:

[source,shell]
----
changelog 4.0.x
----

[source]
----
Generation: 4.0

 Branch:   4.0.x    <-- Branch tip 🚤
  Tags:    4.0.3
           4.0.4    <-- Latest release on the line 🔀

 Range:    4.0.4..4.0.x
----

A line without a release tag fails as a first release.
Other branches (`main`) and bare commits carry no version identity to infer a lower bound from; both cases require an explicit range.

[[resolution-rules]]
==== Resolution rules

The diagrams follow from two rules:

* *Lower bound* (`from`): the previous release.
A patch uses the previous patch (`4.0.4` against `4.0.3`).
A line opener (a version with a trailing zero, such as `4.1.0`) uses the opener of the preceding line: a minor against the previous minor (`4.1.0` against `4.0.0`), a major against the opener of the previous major's most recent line (`4.0.0` against `3.5.0`).
A maintenance branch uses the latest release on its line.
* *Upper bound* (`to`): an existing tag for the version (which regenerates released notes), otherwise the maintenance-branch tip (`4.0.x`, preferring a local branch, then `origin`, then any other remote) for a patch, otherwise `HEAD` for a line opener.

`changelog` stops rather than guessing when the history is incomplete: a missing predecessor between existing releases is a gap, a target with no earlier release a first release, and both require an explicit range (see <<explicit-ranges>>).

Use `--resolve-previous` to print the resolved previous version and exit.

[[explicit-ranges]]
=== Explicit ranges

An explicit range supplies both bounds, as two arguments or in Git's two-dot notation:

[source,shell]
----
changelog 4.0.0 4.0.4
changelog 4.0.0..4.0.4
----

The two forms are equivalent.
An empty upper bound (`4.0.0..`) means up to `HEAD`.
Three-dot notation is not supported.

Each bound resolves independently, in order: as a Git revision, as a branch name, and finally as a version matched against the tags.
An interpretation that cannot complete the range falls through to the next, so a branch named like a version does not shadow the version.

[cols="1,2",options="header"]
|===
| Bound | Resolves to

| A revision (`v4.0.0.RELEASE`, a commit SHA, `HEAD`, `v4.0.0~2`)
| the revision, as Git resolves it.

| A branch name (`4.0.x`)
| the branch tip, preferring a local branch, then `origin`, then any other remote.

| A version as lower bound (`4.0.0`)
| the tag releasing that version across spellings (`v4.0.0.RELEASE` in a repository that tags this way).
An untagged version is an error, because it denotes no commit.

| A version as upper bound (`4.0.4`)
| the tag when present, otherwise the maintenance-branch tip for a patch or `HEAD` for a line opener, as in <<releasing-a-version>>.
|===

The header shows the resolved form (`v4.0.0.RELEASE`, `origin/4.0.x`), not the input spelling.

== Configuration

=== File location and precedence

On its first run in a repository, Changelog Tool writes a configuration file with defaults: `.github/changelog.json` when the repository contains a `.github` directory, `.changelog/changelog.json` otherwise.
When both files exist, `.github/changelog.json` takes precedence.
An existing file is never moved or duplicated, and an invalid file is an error rather than silently replaced, so a typo cannot quietly change which entries appear in your notes.

=== Keys

[cols="1,3",options="header"]
|===
| Key | Description

| `sections`
| An ordered list of sections. Each section has a `title` (the Markdown heading), a list of `labels` to match, and an optional `summary` (a short word shown in the run summary, such as `features`). Order is significant: a change is placed in the first matching section.

| `excludeLabels`
| Labels that cause a matching change to be omitted from the notes entirely.

| `team`
| GitHub logins that are never credited in the Contributors section, matched ignoring case. By default this contains the authenticated user.

| `followReferences`
| An optional allow-list of `owner/repo` patterns for cross-repository references, where `*` matches one or more characters. A new configuration is seeded with `<owner>/*`. An absent or empty list follows every reference.
|===

[[cross-repository-references]]
=== Cross-repository references

A cross-repository reference is looked up only when its `owner/repo` matches `followReferences`.
A reference held back this way produces no changelog entry and no contributor credit.
References to the repository being released are always followed.

=== ZeroConf™ (default configuration)

[source,json]
----
{
  "sections": [
    { "title": ":star: New Features", "labels": ["enhancement"], "summary": "features" },
    { "title": ":lady_beetle: Bug Fixes", "labels": ["bug", "regression"], "summary": "bugs" },
    { "title": ":notebook_with_decorative_cover: Documentation", "labels": ["documentation"] },
    { "title": ":hammer: Dependency Upgrades", "labels": ["dependency-upgrade"] }
  ],
  "excludeLabels": ["type: task"],
  "team": ["<your login>"],
  "followReferences": ["<owner>/*"]
}
----

TIP: To re-categorize changes, adjust the `labels` of a section or reorder the sections.
To hide a class of changes, add their label to `excludeLabels`.
To include changes that match no section, run with `--all`.

=== Caching

Resolved tickets are cached at `.changelog/<repo>.cache.json` under the working directory, keyed by repository and number, so later runs avoid repeated network requests.
Pass `--refresh` to bypass the cache and re-fetch.
The cache is regenerable; a corrupt file is rebuilt rather than failing the run.
